---
title: Limits
description: What filmstrip can't do on each backend, and what happens when you hit it.
---

When a backend can't do something, filmstrip refuses it by name or reports it on the plan, so nothing fails silently.
This page collects those limits in one place.

## Stream copy

An export copies its streams without re-encoding whenever it can. `ExportPlan.copyBlockedBy` lists every reason it
couldn't, so you can see what to drop to get the copy back. See [Export](/guides/export/).

| What blocked it  | `CopyBlocker`                                                                                             |
| ---------------- | --------------------------------------------------------------------------------------------------------- |
| The spec         | `FrameRateSet`, `VideoCodecNamed`, `AudioCodecNamed`, `HeightSet`, `BitrateSet`                           |
| The edit's shape | `MultipleTracks`, `MultipleClips`, `TrackStartsLate`, `TrackDropsAStream`, `FrameResized`                 |
| Effects          | `CompositionHasEffects`, `TrackHasEffects`, `ClipHasEffects`                                              |
| Audio            | `AudioSpecChanged`, `CompositionGainChanged`, `TrackGainChanged`, `ClipGainChanged`                       |
| Timing           | `ClipSpeedChanged`                                                                                        |
| The source       | `TrimNotOnSyncSample`, `SourceUntimed`, `MuxerRefusesSource`, `SourceCodecUnnameable`, `GradeMustToneMap` |
| The backend      | `BackendCannotCopy`, `NonSquarePixels`                                                                    |

- Setting `quality` blocks as `BitrateSet`. `MatchSource` doesn't block.
- The `Upload`, `Share` and `Archive` [presets](/guides/export/#presets) name a codec, so they never copy. `Original`
  can.
- On Android a source with non-square pixels always transcodes, as `NonSquarePixels`.
- A source whose packets have no timestamps, like an AVI with B-frames, can't be copied when trimmed before its end. It
  transcodes as `SourceUntimed`.
- A copy that ends on a B-frame also writes the few frames that B-frame depends on. A player shows them after the end,
  the preview doesn't.
- On Android a copy only keeps the audio units that end inside its window. A window shorter than one unit, about 21 ms
  of AAC at 48 kHz, writes no audio track and reports `AudioDropped`.
- On ffmpeg, Apple and the browser, a source with more than 1000 packets a second, or one whose packets can't be read,
  is refused at `plan()` as `SourceUnreadable`.

## Probe deadline

On ffmpeg every call to `ffmpeg` or `ffprobe` made while planning, probing or reading a frame has a deadline of 30 s,
plus 10 ms for each second of source. One that runs over fails as `TimedOut`, naming the operation and the deadline.
Nothing is cached, so the next call tries again. If the ffmpeg lookup itself times out, it fails as
`ToolchainMissing` instead. Exports and preview playback have no deadline.

## Encoder color

Some Android encoders write a different color matrix than they were asked for. filmstrip tags the file with what the
encoder actually wrote, so its colors still decode correctly, and reports a `ColorSpaceChanged` adjustment. A
color-managed player can still show greens a shade apart from the preview.

The adjustment only shows up on `ExportStatus.Success`, so a plan can't predict it and a `strict` spec can't refuse it.
See [Export](/guides/export/#run).

## Placement

A clip sits at the same fraction of the frame on every backend, but not every backend can draw a fraction of a pixel.
See [Fit](/guides/effects/#fit).

- Apple and the browser place a clip exactly.
- Android and ffmpeg round to whole pixels, the same way, so they land on the same pixels.
- On an 8-bit ffmpeg export, an overlay or a cropped region at an odd pixel offset lands one pixel up and left of the
  other backends.

## Source alpha

A source with transparent pixels draws over the fill, solid or blurred, even when it covers the whole frame. A track
reports `hasAlpha` only for alpha its backend can decode, and a source whose alpha a backend drops is treated as opaque.

- Android video decoders hand back opaque pictures, so a video with alpha, such as VP9 in WebM or HEVC with alpha,
  reads as opaque there. A PNG or WebP still keeps its alpha.
- ffmpeg decodes VP9 alpha with its native decoder, which drops it, so a WebM tagged `alpha_mode` reads as opaque.
  ProRes 4444 and other formats whose pixel format has an alpha plane keep it.
- A GIF, AVIF, HEIC or JPEG XL still reads as opaque everywhere except Apple.
- On Apple, a ProRes 4444 clip draws through the compositor, which asks for BGRA frames so the alpha arrives. A graded
  HDR export blends in Core Image's own space, not on stored codes.
- The browser decodes VP9 alpha through WebCodecs and composites it over the fill. Images are not a browser source.
- The ffmpeg and Android blends are rounded to the nearest code on the stored channels, so a half transparent pixel can
  differ from another backend by a few codes.

## Preview against the file

A preview doesn't encode, so it never shows compression artifacts. Late frames are dropped, so it can be less smooth
than the file.

- An ffmpeg preview shows the exact frame handed to the encoder, so compression is the only difference.
- On Android the encoder halves color resolution, which shows as slightly different color around the edges of a
  caption. The first few frames of every file are a little further off.
- Fading a large picture overlay on ffmpeg is slow while the opacity moves, about 27 ms a frame for a 1080p picture.
  Frames where it holds are fast.

## Relaxed seek

A `SeekAccuracy.Nearest` seek lands on a nearby frame, and its `SeekCompleted` says which one.

| Backend | Where a `Nearest` seek lands                          |
| ------- | ----------------------------------------------------- |
| Apple   | The nearest keyframe within 250 ms, either side       |
| Browser | The keyframe at or before the target                  |
| Android | The exact frame, so it's no faster than an exact seek |
| ffmpeg  | The exact frame, once a scrub settles                 |

## Shuttle

A shuttle shows as many frames as the backend can land, so how a frame lands sets how smooth it looks.

| Backend | Where a shuttle frame lands                                                                         |
| ------- | --------------------------------------------------------------------------------------------------- |
| Apple   | A keyframe between the frame showing and the playhead, up to 250 ms short of it, or the exact frame |
| Browser | The exact frame                                                                                     |
| Android | The exact frame                                                                                     |
| ffmpeg  | Nowhere, it has no shuttle                                                                          |

On Android every frame is decoded from the keyframe before it. Measured on a flagship phone with the VHS filter on,
1080p shows 24 to 31 frames a second forwards and 20 to 22 in reverse. 4K shows about 10 forwards and 7 in reverse.

## HDR text and pictures

On an HDR grade an overlay keeps the brightness its colors have elsewhere in the frame, and fades and soft edges blend
naturally, on every backend. The exception is Android on an HLG grade, which is close but not exact, and the plan
reports it as approximated. See [Overlays](/guides/overlays/) and [HDR](/guides/hdr/).

## HDR on older Android

media3 refuses to decode an HDR source below API 29, so the plan refuses any export there that would decode one: a
tone map to SDR, and a kept grade that re-encodes. A copy decodes nothing, so it still keeps the grade.

## Overlay pictures on older Android

Android's own decoders set what an overlay picture can land as, and the plan reports each way one lands short as a
`ColorSpaceConverted` or `PrecisionReduced` adjustment naming the decoder.

- On API 28 the HEIC decoder reads every HEIC at limited range, whatever range the file records, so a full range HEIC
  has its samples turned into RGB at the wrong range. From API 29 it reads the range the file states.
- On API 31 and 32 the AVIF decoder does the same for AVIF, until API 33.
- On API 26 to 28 Android's decoder refuses extended sRGB as a preferred color space and decodes a sixteen-bit picture
  into linear half floats, which filmstrip encodes back to sRGB. Its samples come back within 38 of what the file
  stores, out of 65535, where they come back within 16 from API 29. That is under a fifth of one eight-bit code, the
  depth the overlay is drawn at.

## Audio

On ffmpeg a long clip looped many times can use a lot of memory, up to one decoded pass for each loop still waiting to
play. See [Extra tracks](/guides/audio/#extra-tracks).

On Android a file records the priming its AAC encoder writes, so its audio starts on the first frame. Both software
encoders write 2048 frames, measured on emulators from API 26 to 36. A device that picks a vendor's own AAC encoder gets
the delay media3 assumes for it, which no emulator can measure, so its audio can start off by the difference.

Only an MP4 or QuickTime file gives its tracks ids every backend reads alike. A Matroska or WebM file, an MPEG
transport stream or a raw AAC stream names each audio track by its place among them, counted from one, so the first is
`AudioTrackId(1)`. See [Choosing a track](/guides/audio/#choosing-a-track).

A track's `language` is for showing to a person, not for choosing by. For an MPEG transport stream it differs by
backend, and Apple and the browser report none.

Which audio track is the default comes from these, on each backend:

| Backend | MP4, QuickTime            | Matroska, WebM           | Any other container              |
| ------- | ------------------------- | ------------------------ | -------------------------------- |
| ffmpeg  | The enabled bit in `tkhd` | The track's default flag | ffprobe's default disposition    |
| Apple   | The enabled bit in `tkhd` | Can't open the file      | None flagged                     |
| Android | The enabled bit in `tkhd` | The track's default flag | media3's default selection flag  |
| Browser | The enabled bit in `tkhd` | The track's default flag | None flagged                     |

AVFoundation opens no Matroska or WebM file, from a path or from bytes, so Apple refuses one as `SourceUnreadable`.
On iOS AVFoundation opens no MPEG transport stream either, and Apple refuses one the same way. macOS opens it.

On Android the tracks come from media3's own extractors, once the media3 backend is registered. Without it, core's
prober flags no default track outside an MP4 or QuickTime file, so a clip that names no track plays the first one.

media3 leaves out a track whose codec it can't read, so outside an MP4 or QuickTime file the audio tracks after it are
numbered one lower than ffmpeg numbers them. media3 couldn't play that track anyway.

## Clip speed

Every backend plays clips from 1/32 to 32 times speed with the pitch kept. Sources are decoded in full, so a fast clip
costs more. See [Speed](/guides/edits/#speed).

Each output frame shows the source frame nearest to its time. A clip too short to cover one output frame shows no
picture but still plays its audio. If it's the whole primary track, it's refused as `InvalidComposition`.

- **Android** doesn't duplicate frames in slow motion, so at 1/32 each frame holds for about a second. Its AAC encoder
  adds up to 32 ms of audio at the end of any file.
- **Android** exports open a clip's audio on its trim start at every speed. Past that, Sonic, the stretcher media3
  ships, repeats or drops whole pitch periods of up to 1/65 s, so a sound can land up to max(1, 1/speed - 1) periods
  off. That's 15 ms at 0.5 and 2, and 477 ms at 1/32.
- **Android** previews leave the speed to media3, so a clip's audio opens up to two AAC access units late, scaled by
  the speed. That's 1.49 s for a 44.1 kHz clip at 1/32, and up to 685 ms was measured.
- **Android** drops frames to fit a fast clip to the output rate. Past about 55 minutes of a clip at 30 fps, or 7 at 60,
  the frames it keeps drift off their slots.
- **Apple** writes sped up audio to a temporary file during an export. A clip with more than 10 million frames is
  refused by name.
- **ffmpeg** previews have no audio. A variable frame rate source can show the next or previous frame where a slot
  lands halfway between two.

## Filters

Each [filter](/guides/filters/) looks the same on every backend, within a few code values. Where a backend can't run
one, it's refused by name.

- **Apple** runs `vhs`, `film`, `crt`, `glitch`, `lut`, `nightVision` and `pixel` on Core Image Metal kernels, which
  need an Apple6 GPU on iOS, or macOS 12 on a Mac.
- **Browser** refuses a clip larger on a side than the page's `MAX_TEXTURE_SIZE`. A fit that crops makes the clip's
  frame larger than the output.
- **Android and browser** need OpenGL ES 3 for every filter, and a texture big enough for a `lut` table, 1170×520 for a
  65 point table and 3096×1419 for 129.
- **ffmpeg** blurs with the shared kernel, and rounds through RGB and back, so a hard edge can land a couple of codes
  off. Everywhere else it's within a few code values.
- **ffmpeg** works in 4:2:0, which averages out the colored stripes in `crt`'s mask. Any 4:2:0 file does the same, so
  the export matches the other backends.
- **ffmpeg** holds `nightVision`'s grain to one of 255 steps, and writes it in 4:2:0, which averages each pixel's grain
  colour with its neighbours'. Each plane lands within 1.5 code values of the other backends' signal.
- **ffmpeg** refuses a look its build is missing a filter for.
- **ffmpeg** draws `glitch` with one `geq` over each of red, green, blue and alpha, every pixel a bilinear read at its
  row's shift, and goes through RGB and back to do it. That round trip lands within 3 codes of the signal, and 4:2:0
  averages the colour fringe across two rows where a slice ends.
- **ffmpeg** reads a `vhs` beside a clear canvas bar tap by tap where its blur lands across the bar's edge, which runs
  about 0.9 fps at 1080p on the same server where a frame with no bar runs 5.2 fps. A source with its own alpha can be
  clear anywhere, so it is read tap by tap over the whole frame, which is slower still.
- **Every backend** draws `vhs` tracking snow from the same signal. Apple and Android land within 1e-4, the browser
  within one code, and ffmpeg within 1.74 codes of luma and 1.14 of chroma, since it mixes into 8-bit planes.
- **Every backend** draws `camcorder` from the same raster. Apple and Android land within 1e-4 and the browser within
  one code. ffmpeg lays it on 4:2:0 codes, so luma lands within one code and a coloured edge blends with the pixels
  next to it. A pixel inside a colour lands within one code.
- **ffmpeg** refuses a `camcorder` over a span with no end.

Filters are heavy on ffmpeg. Measured on a 12 thread x86 server with x264:

| Look                              | 1080p    | 4K       | Peak memory, 1080p and 4K |
| --------------------------------- | -------- | -------- | ------------------------- |
| `film`                            | 18.4 fps | 9.2 fps  | 1 GB and 3.4 GB           |
| `vhs`                             | 5.2 fps  | 2.1 fps  | 1 GB and 3.3 GB           |
| `crt`                             | 9.0 fps  | 2.4 fps  | 1.5 GB and 5.4 GB         |
| `lut`                             | 70 fps   | 21 fps   |                           |
| `Film.Super8`                     | 0.3 fps  | 0.1 fps  |                           |
| `glitch`                          | 4 fps    | 1 fps    |                           |
| `nightVision`                     | 24.8 fps | 6.9 fps  |                           |
| `pixel`                           | 54 fps   | 23.1 fps |                           |
| `pixel` with a palette and dither | 31.6 fps | 19.1 fps |                           |
| `vignette`                        | 18.8 fps | 4.8 fps  |                           |
| `gaussianBlur` at 0.02            | 40.3 fps | 9.5 fps  |                           |

- `Film.Super8`'s weave is a per-pixel expression on ffmpeg, since no built-in filter reproduces its sub-pixel read
  exactly. `glitch` is one too, for its per-row shift.
- `crt` on each clip adds about 550 MB per 1080p clip. When every clip has the same `crt` at the output size and
  they join with no gap, it runs once over the whole export instead.
- `film` and `vhs` fall back to a slower path with the same result when the JVM can't open a local socket, the ffmpeg
  build has no `tcp` protocol, or the graph would need more than 16 live inputs. `vhs` also falls back for a source not
  tagged BT.709. The diagnostics name the fallback.
- A `vhs` with snow opens three live inputs and one without opens two, so five snowy clips run live and a sixth falls
  back. A 1080p `vhs` with a snowy band always in frame ran about 16 fps live and 7.8 fps on the fallback, on ffmpeg
  9.0.2 on an arm64 Mac.
- Changing a `crt` in a preview restarts ffmpeg, which takes 0.6 to 1.7 s to the first frame.

## Preview on iOS 27

On the iOS 27.0 simulator, a preview fails before it plays. Its status is `PlaybackStatus.Error` with a
`PlaybackError.Underlying` whose `platformCode` is -11800 and whose message ends `(NSOSStatusErrorDomain -12784)`.
Apple's own video compositions fail the same way with no filmstrip code involved.

- `play()` does nothing after the failure. Setting a new composition tries again.
- Exports still work.
- The iOS 27.2 simulator plays. Physical devices on iOS 27 haven't been tested.

## Sinks

`MediaSink.Uri` takes only `file://` on Apple and ffmpeg, and ffmpeg also takes a bare path. Anything else is refused as
`SinkUnwritable`. Android writes to any URI its content resolver can open. The browser ignores the URI and hands back an
object URL. See [Sinks](/guides/sources-and-sinks/#sinks).

## In-memory sources

On Android, Apple and ffmpeg a `MediaSource.Bytes` is written to a temporary file before it's read. Those files are
cleared by the next process that reads a buffer, so disk use grows with the number of different buffers one process
reads. The browser keeps the buffer in memory. See [Sources](/guides/sources-and-sinks/#sources).

Some containers can't be read from bytes on Apple, and are refused as `SourceUnreadable`, the same as a path would be.

| Container        | macOS | iOS Simulator |
| ---------------- | ----- | ------------- |
| Matroska, WebM   | ✗     | ✗             |
| Transport stream | ✓     | ✗             |

Android can't read a QuickTime file with no `ftyp` box, from bytes or a path. Apple and ffmpeg can.

## Browsers without WebCodecs

In a browser, filmstrip decodes and encodes only through WebCodecs, with no fallback. Firefox for Android has none of it
as of November 2026.

| Missing        | What happens                                                                                                |
| -------------- | ----------------------------------------------------------------------------------------------------------- |
| `VideoDecoder` | A preview with video fails with `PlaybackError.UnsupportedFormat`. Thumbnails fail too.                     |
| `AudioDecoder` | A preview plays silently and doesn't report `AudioMonitoring`. An audio-only preview fails.                 |
| `VideoEncoder` | Previews work. `capabilities()` lists no video encoder, and a plan refuses with `FilmstripError.NoEncoder`. |
| `AudioEncoder` | Exports have no audio, and their previews are silent to match.                                              |

The demo on this site checks the same things, and says so in place of the LOAD button. See [Player](/guides/player/).
