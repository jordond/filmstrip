Each limit is named once here, with a link to the page that explains the feature around it.

## Stream copy

An export that can copy its streams does, with no re-encode. `ExportPlan.copyBlockedBy` lists every reason one didn't,
so you can see what to drop to get it back. See [Export](/guides/export/).

| Source of the block | `CopyBlocker`                                                                             |
| ------------------- | ----------------------------------------------------------------------------------------- |
| The spec            | `FrameRateSet`, `VideoCodecNamed`, `AudioCodecNamed`, `HeightSet`, `BitrateSet`           |
| The edit's shape    | `MultipleTracks`, `MultipleClips`, `TrackStartsLate`, `TrackDropsAStream`, `FrameResized` |
| Effects             | `CompositionHasEffects`, `TrackHasEffects`, `ClipHasEffects`                              |
| Audio               | `AudioSpecChanged`, `CompositionGainChanged`, `TrackGainChanged`, `ClipGainChanged`       |
| Timing              | `ClipSpeedChanged`                                                                        |
| The source          | `TrimNotOnSyncSample`, `MuxerRefusesSource`, `SourceCodecUnnameable`, `GradeMustToneMap`  |
| The backend         | `BackendCannotCopy`                                                                       |

Every built-in backend can copy, so none of them reports `BackendCannotCopy`. `quality` blocks as `BitrateSet`, and
`MatchSource` doesn't block at all.

`Upload`, `Share` and `Archive` each name a codec, so those [presets](/guides/export/#presets) never copy. `Original`
keeps the copy open.

## Encoder color

Some Android encoders write a different color matrix than they were asked for. filmstrip tags the file with what the
encoder writes, so its colors decode as authored, and reports a `ColorSpaceChanged` adjustment. Android names primaries
and matrix together, so a file tagged BT.601 records BT.470 BG primaries too, and a color-managed player can show greens
a shade apart from the preview.

That adjustment only arrives on `ExportStatus.Success`. A plan can't see it, so a plan can say `Capable` and a `strict`
spec can't refuse it. See [Export](/guides/export/#run).

## Placement

A clip's placement is the same fraction of the frame on every backend, but not every backend can draw a fraction of a
pixel. See [Fit](/guides/effects/#fit).

- media3 draws a frame's edge on a pixel edge, and `scale`, `crop` and `pad` in ffmpeg take whole pixels. Both round the
  placement the same way, so they land on the same pixels.
- On a 4:2:0 chain, ffmpeg's `pad` and `overlay` land an odd offset on the even pixel below it. A canvas built by a
  `crop` with `Fit.Contain` or `Fit.Stretch` moves to 4:4:4 where it has an odd figure, so it lands exact.
- Apple and the browser place a clip at its exact fraction.

## Preview against the file

An ffmpeg preview ends its graph on the format the export writes and converts from there for the screen, so it shows the
frame the encoder is handed, and encoder loss is all that's left between the two. That holds on a caption, a picture, a
grade and an HDR grade, at every speed. A graph that doesn't already end on that format pays for one more conversion.
At 1080p on ffmpeg 9.0.2 a caption read 478 frames per second against 543 without it, and a composition grade 469
against 516.

An overlay runs on every frame of its plan, so a frame outside its window goes through the same conversions as one
inside it, in the file and in the preview.

A media3 preview and its file part in chroma around a caption, because the encoder reduces chroma to 4:2:0 and a preview
keeps every pixel's. On an API 36 emulator the software `c2.android.avc.encoder` takes each 2x2 block's chroma from its
top left pixel, which puts a Cb about 1 code from the preview's top left where a box average sits about 5 away. Past a
file's first 8 frames luma reads 47 to 52 dB against the file on API 30 and API 36, at 1/32, 0.7, 1.5 and 32, and the
bitrate doesn't move the chroma. Hardware encoders aren't measured, so what filmstrip tests is the bound any of them
holds: past those frames each block's chroma stays within 3 codes of the preview's range over that block and the pixels
around it. The encoder's first 8 frames sit further off at every speed, speed 1 included, by up to 16 codes of chroma and
down to 44 dB of luma, and a short clip at 1/32 writes few frames past them.

## HDR text and pictures

On an HDR grade, an opaque overlay texel lands at the light a fill of that color lands at, and soft edges, fades and
opacity blend in linear display light. That holds on every backend, ffmpeg included. The one exception is media3 on an
HLG grade, which holds the frame as scene light and blends there, and the plan reports it as an approximated effect. See
[Overlays](/guides/overlays/) and [HDR](/guides/hdr/).

## Audio

ffmpeg splits a looping clip into one branch per pass, and up to one pass of decoded media sits in memory for each
branch still waiting. A long clip looped many times costs that much memory. See
[Extra tracks](/guides/audio/#extra-tracks).

## Clip speed

Every backend plays 1/32 to 32 with the pitch kept and decodes its sources in full, so the cost scales with the speed.
Each file runs the shared output length, give or take its last frame and its audio tail. What's left is each backend's
own. See [Speed](/guides/edits/#speed).

| Backend      | Limit                                                                                     |
| ------------ | ----------------------------------------------------------------------------------------- |
| AVFoundation | An export renders sped audio to temporary disk, 16-bit PCM for the output length.         |
| media3       | The AAC encoder runs at most 32 ms past the output length.                                |
| media3       | On API 30 the AAC encoder ends up to 55 ms before the output length, at any speed.        |
| media3       | Slow motion is sparse. Nothing duplicates a frame, so a clip's frames sit apart by speed. |
| ffmpeg       | A preview has no audio, at any speed.                                                     |

Sparse slow motion means a clip at 1/32 from a 30 fps source holds each frame for about a second. The file plays, and its
last frame was measured running 457 ms past the output length when the trim cuts that frame short. The other backends
write every output slot. A media3 preview reads whole milliseconds, so a read within 1 ms of a frame's own time can land
on either side of it. The AAC tail is what the encoder adds at the end of the stream, and a clip at speed 1 has it too.

On API 30 `c2.android.aac.encoder` flushes nothing at the end of the stream and keeps only the whole access units it was
fed, so the last of the audio never reaches the file. On an emulator that measured 33 to 53 ms, and the same PCM through
the same encoder on API 36 keeps all of it. The levels between aren't measured. An export that copies its audio isn't
affected.

## Filters

[Filters](/guides/filters/) draw one shared signal on every backend, and these are where a backend lands apart from it or
refuses.

- An Apple device that can't compile a Core Image Metal kernel, which takes iOS 15 or macOS 12 on an Apple6 GPU, refuses
  `vhs` by name.
- The browser draws a shader pass on a clip's whole frame, so a clip whose own frame is longer on a side than the page's
  `MAX_TEXTURE_SIZE` is refused by name. A fit that crops makes that frame bigger than the output.
- ffmpeg blurs with `gblur`, a recursive approximation of a Gaussian that lands narrower than the sigma it's given. A hard
  edge reads up to about a fifth of its step off, the frame's own edge against the black past it included. Anywhere else
  it's within a few codes.
- Below about 0.005 pixels `gblur`'s own filter darkens the frame, so a blur smaller than 0.01 pixels runs at 0.01, which
  changes no pixel.
- An Apple device that can't compile a Core Image Metal kernel refuses `crt` by name too.
- ffmpeg carries a frame in 4:2:0, which can't hold the stripes of colour in `crt`'s phosphor mask. Luma keeps them, within
  3 codes of the other backends, and chroma holds their mean over each sample, within 3 codes. An encoded 4:2:0 file
  is the same on every backend.
- ffmpeg builds `crt`'s map once, as eight frames read from scratch files, and draws from them in sixteen-bit red, green
  and blue. With an x264 encode that ran at about 10 fps at 1080p and 2.6 fps at 4K on an x86 server, where `film` ran at
  about 2 fps at both. It peaks near 1.5 GB at 1080p and 5.4 GB at 4K, and a `crt` on a clip or a track adds about 550 MB
  per 1080p clip, since ffmpeg holds each clip's working frames until the export ends. Clips of one size share the eight
  frames.
- An Apple device that can't compile a Core Image Metal kernel refuses `lut` by name too.
- `lut` on media3 and the browser reads its table from a texture 2 times `ceil(sqrt(N))` tiles wide, so a grid of 65 points
  takes 1170x520 and a grid of 129 takes 3096x1419. A GL context whose `MAX_TEXTURE_SIZE` is smaller fails by name, and media3
  and the browser need OpenGL ES 3.
- ffmpeg reads `film` grain, and `vhs` grain and dropouts, from planes filmstrip draws in Kotlin and hands over a
  loopback TCP socket, at the same samples a `geq` would write. Measured on ffmpeg 8.0.1 on a 12 thread x86 server with
  x264 medium, `film` runs about 17.5 fps at 1080p and 7.9 fps at 4K against 2.05 and 1.96 on `geq`, and `vhs` about 9.1
  and 2.8 against 6.75 and 2.3. Peak ffmpeg memory for `film` was about 1 GB at 1080p and 3.4 GB at 4K, and for `vhs`
  about 1 GB and 3.3 GB.
- A plan falls back to the `geq` graph by name in the diagnostics, as the same samples and slower, when the JVM cannot
  bind a loopback listener, when the ffmpeg build has no `tcp` protocol, when a graph would open more than 16 live
  inputs, and for `vhs` when a source is not tagged BT.709. ffmpeg offers no way to copy one pad's matrix onto another,
  and a VHS map carries chroma that a conversion would move.
- A plan where every clip runs one equal `crt` at the output's size, decoded as plain 4:2:0 and joined with no gap, runs
  the look once after the join. That took 12 clips at 1080p from 5.5 GB to about 1.9 GB. `film` and `vhs` stay on each
  clip, since they read a frame's own timestamp and the join moves it.
- Changing a `crt` in a preview restarts ffmpeg like any graph change, measured at 0.6 to 1.7 s to the first frame on the
  same server.
- `lut` on ffmpeg passes through RGB and 4:2:0 on its way back to the encoder. Measured on ffmpeg 8.0.1 x86_64, luma lands
  within 1.72 codes of `CubeLut.at`, chroma within 1.17, and a channel read back as RGB within 2.59.
- ffmpeg draws `lut` through `lut3d` on `gbrap`. With an x264 veryfast encode and a 65 point table that ran at about 70 fps
  at 1080p and 21 fps at 4K on a 12 thread x86 server, against 300 and 85 fps with no table.
- A build missing a filter a look runs on refuses it by name, like any other effect.

## Preview on iOS 27

On the iOS 27.0 simulator runtime, a preview shown through an `AVPlayerLayer` in a window fails before play, a seek or a
first frame, and its status can read `Ready` for a moment first. An item with a video composition fails this way, and
every preview with video has one. A plain item with no video composition reached ready. In the sample app a 720p H.264
clip, the same clip trimmed and a 1080p H.265 clip all failed. So did a composition from Apple's
`videoCompositionWithPropertiesOfAsset` with no filmstrip code in it, tried once in the sample.

On the iOS 27.2 simulator runtime the 720p H.264 clip played in the sample. The trim and the H.265 clip reached ready
there and weren't played through. On the iOS 26.5 simulator runtime a test read a video composition item in a window
reaching ready, without playing it or reading a picture.

- The player's status is `PlaybackStatus.Error` with a `PlaybackError.Underlying`. Its `platformCode` is -11800 and its
  message ends with `(NSOSStatusErrorDomain -12784)`. One `PlaybackEvent.Failed` reports it for each failed item.
- `play()` on that item starts nothing and the status stays `Error`. Setting a new composition is what tries again.
- An `AVPlayerItemVideoOutput` on an item with a video composition fails the same way on that runtime, with no layer.
- Export isn't stopped there. In the sample the 720p H.264 clip whose preview had just failed exported and re-probed at
  its full length, and filmstrip's tone map export tests and one other Apple export test pass on fixtures on that runtime.
  Other clips and edits weren't exported.

A physical iPhone on iOS 27 is unmeasured, so whether a device does this too isn't known yet.

## Sinks

`MediaSink.Uri` is `file://` only on Apple and ffmpeg, and anything else is refused as `SinkUnwritable`. ffmpeg also
takes a bare path there. Android writes to any other scheme through its content resolver. The browser ignores the URI
and hands back an object URL. See [Sinks](/guides/sources-and-sinks/#sinks).

## In-memory sources

On Android, Apple and ffmpeg a `MediaSource.Bytes` is written to a file before it is read, and the file stays until a
later process first uses a buffer. Disk use grows with the distinct buffers a process reads, with no bound. The browser
keeps the buffer in memory. See [Sources](/guides/sources-and-sinks/#sources).

ffmpeg writes under a directory named for the user in the shared temporary directory. If another user already holds
that name, the process writes to a private directory of its own instead, removed when the JVM shuts down.

AVFoundation goes by a file's name, so filmstrip names a buffer's file from its leading bytes, the same names a path
would carry. A buffer of a container AVFoundation doesn't open reads as `SourceUnreadable`, the same as a path does:

| Container        | macOS | iOS Simulator |
| ---------------- | ----- | ------------- |
| Matroska, WebM   | No    | No            |
| Transport stream | Yes   | No            |

Android's platform extractor refuses a QuickTime file with no `ftyp` box, so such a buffer reads as `SourceUnreadable`,
the same as a path to that file does. Apple and ffmpeg read it.

## Browsers without WebCodecs

WebCodecs is the only way filmstrip decodes or encodes in a browser, and there's no fallback. Firefox for Android has
neither half, per caniuse as checked on 2026-11-06.

- With no `VideoDecoder`, a preview of anything with video fails before it reads a source. Its status is
  `PlaybackStatus.Error` with a `PlaybackError.UnsupportedFormat` saying "This browser has no WebCodecs video decoder, so
  it can't preview video." An `AudioSpec.AudioOnly` composition draws nothing, so it needs an `AudioDecoder` instead.
- With no `AudioDecoder`, a preview of anything with video plays silently and doesn't report
  `PlayerFeature.AudioMonitoring`. An `AudioSpec.AudioOnly` composition has nothing to play, so it fails before it reads
  a source, with a `PlaybackError.UnsupportedFormat` saying "This browser has no WebCodecs audio decoder, so it can't
  preview audio."
- With no `VideoEncoder`, a preview runs as normal and carries its audio. `Filmstrip.capabilities()` lists no video
  encoder, and a plan refuses with `FilmstripError.NoEncoder`, so check `video` on the capabilities to know an export
  can't run.
- With a `VideoEncoder` and no `AudioEncoder`, an export writes no audio and its preview matches it, so both are silent.

Thumbnails need a `VideoDecoder` too. With none, each request fails with a `FilmstripError.InvalidComposition` carrying
the same words as the preview.

The demo on this site reads the same two globals. With no `VideoDecoder` it keeps the colour bars and says so where LOAD
would be, and nothing downloads. See [Player](/guides/player/).
