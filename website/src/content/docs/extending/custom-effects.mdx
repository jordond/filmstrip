A custom effect has two halves. An `EffectSpec` is data that describes it, shared across platforms. An `EffectResolver` turns
that data into something the current platform can render.

## The spec

<Snippet file="commonMain/kotlin/dev/jordond/filmstrip/docs/extending/CustomEffects.kt" region="spec" />

- `id` has to be stable. Namespace it like a package, so two libraries can't collide, and never derive it from the class
  name.
- `stage` defaults to `EffectStage.Color`. Your effect lands at the end of whichever stage it names.
- `scope` defaults to `EffectScope.Everywhere`. An effect whose result depends on where a frame sits in its run overrides it
  with `ClipOnly`, and a plan refuses it anywhere else.
- `requiresSdr` defaults to `false`. An effect that needs SDR frames says `true`, and an HDR source tone maps first.
  `HdrMode.Auto` reports that as a concession naming your effect, and `HdrMode.KeepHdr` is refused by name.
- `isInert` defaults to `false`. Say `true` when the spec as configured leaves every pixel alone, and the plan leaves the
  effect out and lists it on its [inert notices](/guides/export/#inert-notices), so no backend is handed it.
- `beneathOverlays` defaults to `false`. Say `true` on an `EffectStage.Composite` effect that runs over the fill and under
  every overlay at its own scope, like [`vhs`](/guides/filters/). Outside that stage it changes nothing.

A spec has to compare by value, which a `data class` gives you. filmstrip compares specs to decide if a composition changed
and if a cached thumbnail is still good, so one left on identity equality rebuilds the graph and misses the cache every
time.

Use your extension like any other effect.

## The resolver

A resolver answers one spec at a time. Return `null` to decline it, and the next resolver gets a look.

<Snippet file="commonMain/kotlin/dev/jordond/filmstrip/docs/extending/CustomEffects.kt" region="resolver" />

A non-null answer claims the spec, which ends the chain.

- `EffectResolution.Resolved` renders it as declared.
- `EffectResolution.Degraded` renders it with named `causes`, which `plan` reports before any work starts.
- `EffectResolution.Unsupported` refuses it by name, and no later resolver can substitute another rendering.
- `EffectResolution.Failed` refuses the export with its `error` when a read the effect needs failed, like a decode that
  ran out of time. A later call may succeed, so `withoutUnsupported` never leaves the effect out.

Each platform's answer is a `PlatformEffect`, in that platform's own terms. Gate on `capabilities.api` and decline what you
didn't write for. `attributes` holds what the pipeline already worked out, so multiply a fraction by `inputSize` to get
pixels, the frame size entering this effect. Return a fresh `PlatformEffect` each time, since each plan holds its own.

On ffmpeg a clip with non-square pixels reaches your fragment in one of two shapes. A `Geometry` or `Composite` effect
always gets square pixels, and `inputSize` is the frame it draws on. A `Color` or `Spatial` effect runs on the frame as
it's stored, which `attributes.storedSize` holds, while `inputSize` is the size it shows at. A spatial effect that
measures in pixels works out each axis from both, so its reach is the one the viewer sees.

The resolver's `softFocusOn` is an `expect` function you declare yourself, whose `actual` on each platform calls that
platform's function below.

An effect that has to do async work first, like decoding an image in a browser, overrides `prepare`, which runs before each
negotiation of a composition.

## Register it

Resolvers are asked newest registration first, so add yours after the backends.

<Snippet file="commonMain/kotlin/dev/jordond/filmstrip/docs/extending/CustomEffects.kt" region="register" />

A spec no resolver claims is refused by name at plan time.

<Aside type="note" title="Limits">
A `PlatformEffect` in the browser is a `WebGlPass`. One with no `WebGlStep`s is folded into the compositor's own draw
through its texture matrix or color matrix uniform, and the compositor refuses a pass that gives it neither.

A fragment shader on the browser or on media3 reads straight color, not color multiplied by alpha, and writes straight
color back, whatever the frame under it holds.
</Aside>
